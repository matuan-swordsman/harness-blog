# 第 6 篇：Review 分级 + 熵清理 + 复盘（让体系长期有效）

> 系列导航：[总览](README.md) · [上一篇](part-05-harness-gate.md)

> 目标：搞定"机器全绿之后"的事——用**分级 Review** 守住高风险变更，
> 用 **TECH_DEBT / QUALITY_SCORE / doc-gardening** 做熵清理，并盘点最容易踩的坑。

---

## 1. 全绿 ≠ 可合并：引入 Review 分级

机器门禁证明"代码没破坏机械不变量"，但"改对了方向吗"仍需人（或更强的 AI）判断。
如果所有变更都要人工 Review，人又会成为瓶颈。解法是**按风险分级**：

| 变更类型 | 自动测试 | AI Review | 人工 Review |
|---|---|---|---|
| 注释 / 文档 / 脚本 | ✓ | 可选 | 否 |
| 普通业务代码 | ✓ | ✓ | ✓ |
| 新增 API / 接口契约 | ✓ | ✓ | ✓ |
| 依赖方向 / ProjectReference | ✓ | ✓ | **必须** |
| DB 结构 / EF 映射 | ✓ | ✓ | **必须** |
| 认证 / 凭据 / 生产配置 | ✓ | ✓ | **必须** |

Review 只对 **Blocker / Major** 说"不"：

- **Blocker**：安全漏洞、数据丢失、API 契约破坏、并发安全、架构依赖违规、凭据硬编码
- **Major**：异常处理缺失、明显性能问题（N+1 / 阻塞调用）、破坏日志/DI/配置约定、生产逻辑缺测试且未 `tdd-ignore`
- **Minor（不阻塞）**：命名、注释、可拆分重构建议

> 这背后是"吞吐量改变合并理念"：Agent 吞吐量远超人脑注意力时，**纠错成本低、等待成本高**。
> 所以只保留机器可验证的合并门 + 少数高风险人工门，而不是每个 PR 都层层设卡。

## 2. 熵清理：技术债是高息贷款，小步还

Agent 会复制仓库已有模式（包括不好的），时间一长必然漂移。这就是"熵"。
OpenAI 的做法类比 GC：**每天都还一点小额债**，而不是攒一年再痛苦清算。

### 落到本示例的三件套

**① TECH_DEBT.md —— 显式记账**

```markdown
| 日期 | 描述 | 影响 | 状态 |
|---|---|---|---|
| 2026-xx-xx | 某处临时用了 tdd-ignore | 该路径暂无测试 | 待补 |
```

**② QUALITY_SCORE.md —— 定期体检**

给每层、每份文档打分（是否与代码一致、是否最新），分数长期下滑 = 需要介入的信号。

**③ doc-gardening —— 让"文档漂移"也成为门禁**

第 2 篇的 `check-docs.ps1` 已覆盖"文档是否编目、链接是否有效"。更进一步的 `doc-gardener`
会扫描"文档引用的代码路径是否还存在 / 文档是否过期"。
> 本示例把 `doc-gardener`、覆盖率门禁登记为**演进方向**（见示例工程 `docs/harness.md` §6），
> 说明：质量门是分阶段建设的，不必第一天就全上。

### 把"人的品味"编码回去

当 Review 里反复出现同一类问题（比如"又有人绕过 DI 直接 new HttpClient"），
把它变成规则（lint / 测试 / 门禁阶段），而不是每次口头提醒。这是本系列一以贯之的动作。

## 3. 常见坑（本系列与真实项目总结）

1. **AGENTS.md 写成 300 行手册** → 违反渐进式披露，挤爆 Agent 上下文且很快过时。地图只放入口和铁律。
2. **修 lint 只求变绿、不按 Fix 语义修** → 例如 `#region` 的 Fix 是"拆类/拆文件"，直接删标记
   代码还在原类里，问题没解决。规则报错必须带 Fix 语义。
3. **基线机制成为逃避新债的后门** → 基线只装存量；新增违规应修复或走 `tdd-ignore`/lint-ignore 显式登记。
4. **环境性失败当代码失败（或反过来）** → 本地 WARN / CI `-Strict` 分级，别一刀切。
5. **规则只写文档不机器化** → 文档是说教，测试/lint 是执法。能机器化的先机器化。
6. **所有变更一刀切人工 Review** → 瓶颈在人；用分级把注意力留给高风险变更。
7. **给纯展示层套 TDD 覆盖率门禁** → 不变量为真实风险服务；前端页面强套覆盖率只会催生"凑数测试"。
8. **失败输出对 Agent 不可读** → 没摘要、没 Fix、没下一步，Agent 只能瞎试。反馈 = 摘要 + Fix + 重跑路径。

## 4. 能力成熟度速查（你的仓库在第几层？）

| 层级 | 特征 | 收益 |
|---|---|---|
| L1 | 能 build / test，靠人自觉守纪律 | 代码能跑，但一放 AI 就漂移 |
| L2 | 有 AGENTS.md + docs，有 check-docs | Agent 知道去哪看、文档不再孤岛 |
| L3 | 架构测试 + lint 基线 + TDD 门禁 | 越层/坏味道/缺测试被机器拦截 |
| L4 | harness.ps1 一键门禁 + CI | "改码 → 一键 → 全绿/指引"闭环 |
| L5 | 分级 Review + TECH_DEBT/QUALITY_SCORE/doc-gardening | 体系长期有效，熵可控 |

本系列做完，你至少到 **L4**；第 6 篇的机制让你往 **L5** 走。

## 5. 系列总结

我们从"为什么要 Harness"出发，把一个四层 WebAPI 一步步武装成：

```
AGENTS.md（地图）
  ├─ docs/（知识库 + check-docs 文档门禁）
  ├─ 架构测试（依赖矩阵 = 机器强制）
  ├─ lint（禁止模式 + Fix + 基线）
  ├─ TDD 门禁（新增/修改必须配套测试）
  └─ harness.ps1（一键编排 + CI）
        └─ Review 分级 + 熵清理（人只盯高风险）
```

**一句话收尾**（呼应 OpenAI 文章）：
> 构建软件仍然需要纪律，但纪律更多地体现在**支撑结构**上，而不是代码上。
> 你花在"把规则变成机器、把知识放进仓库"上的功夫，会让 AI 时代的吞吐量变成复利，而不是灾难。
